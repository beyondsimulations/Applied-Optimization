# Review: tutorial-06-ordersplit.qmd

**Reviewed:** 2026-07-07
**Scope:** Pedagogy, model formulation, math notation, code, content robustness, writing polish

## Summary

A well-designed tutorial with a strong arc: manual coappearance matrix → manual QMKP solve → split counting → scaled-up JuMP implementation → business interpretation, with self-checking `@assert` cells throughout — genuinely good scaffolding. The main weaknesses: Section 2 says "use the model from the lecture", but the lecture model allows duplicate allocation (`≥ 1`), which changes the hand-solved answer from 7 to 14 and the split count from 3–5 to 0 — the single-allocation requirement is only introduced two sections later; and the split-counting code uses a `> 0` threshold on Juniper/Ipopt solution values where the print code uses `> 0.1`, which can miscount with near-zero numerical noise.

## 1. High-impact teaching improvements

- **State the single-allocation rule in Section 2, not Section 4** (line ~57 vs. ~165). The lecture's QMK model uses $\sum_k X_{ik} \geq 1$, so "the model from the lecture" allows storing a SKU in both warehouses. With capacities 3/3 and the verified Q (pairs: AB=3, AC=2, AD=4, BC=2, BD=0, CD=1), the `≥ 1` optimum is Hamburg={A,B,C}, Berlin={A,C,D} with objective 7+7=14 — and **zero** split orders, which breaks Section 3 and defuses the bonus question. Under single allocation the optimum is 7. Add one sentence to Section 2: "Assume each SKU may only be stored in one warehouse (i.e., the allocation constraint holds with equality)."
- **Surface the multiple-optima insight in Section 3** (line ~68). Under single allocation, *three* partitions all achieve the optimal objective of 7: {A,B,C}|{D} → 5 splits, {A,B,D}|{C} → 3 splits, {A,C,D}|{B} → 3 splits (3 is the minimum over all feasible partitions). Different students will correctly get 5 or 3, and the assignment asks for a single number. Turn this into the teaching moment the bonus question gestures at: "Compare your split count with your neighbour's — did you get the same objective value but a different number of splits? Why?" This makes the QMKP-is-only-a-proxy point concrete instead of accidental.
- **Warn about local optimality before the 141 assert** (line ~314). Juniper is a *local* MINLP solver on this nonconvex binary quadratic problem; the assert accepts `LOCALLY_SOLVED` but then requires the objective to be ≈141. A student with a perfectly correct model can land in a local optimum below 141 and conclude their code is wrong. Add a note ("if you get a lower value with LOCALLY_SOLVED, re-run or check the solver log — Juniper does not guarantee global optimality here") or relax the assert to `>= some bound`.
- **Bridge the string/integer indexing gap.** In the lecture's pattern, `X` is indexed by SKU *names* while `Q` uses *integer* indices, so the objective needs `X[skus[i], warehouses[k]] * ... * Q[i,j]`. This is the tutorial's main stumbling block and it is never mentioned; one hint sentence before the objective cell (line ~249) would save many students a cryptic KeyError.

## 2. Model & notation issues

- **`Model(SCIP.Optimizer())` is wrong** (line ~176): JuMP expects the factory/type, not an instance — `Model(SCIP.Optimizer)`, as the lecture itself does correctly. As written, the recommended SCIP alternative errors immediately.
- **Inconsistent value-rounding thresholds** (lines ~331 vs. ~353): the print code treats a SKU as allocated if `value(X[i,k]) > 0.1`, but `X_values` for split counting uses `> 0`. With Juniper/Ipopt, binaries can come back as 1e-8, which `> 0` classifies as allocated — silently undercounting splits. Use `> 0.5` in both places.
- **The random baseline is not a feasible comparator** (lines ~384–394). `rand(Bool)` allocations can (a) leave a SKU in *no* warehouse (its orders are then counted as "split" though they are unfulfillable), (b) place a SKU in *both* warehouses (an advantage the optimized solution is explicitly denied by the `= 1` constraint), and (c) violate both capacities (up to 12 SKUs in a 7-capacity warehouse). Section 5 then asks "how many fewer split shipments … compared to their current random allocation?" — the fair baseline is a random feasible partition (e.g., shuffle the 12 SKUs, assign the first 7 to Hamburg, the rest to Berlin).
- **`regular_parcels` always equals the number of orders** (lines ~356–378): every transaction increments it, split or not, so it is identically 40 — yet it is printed as "Number of regular orders" (line ~398), which reads as *non-split* orders. Either print it as "total orders/first parcels" or count `regular_parcels` only in the non-split branches.
- **Hardcoded two-warehouse logic** (lines ~365, ~369): `count_split_orders` indexes `X_input[:,1]` and `X_input[:,2]` despite taking generic inputs. A loop over columns (`any(all(X_input[:,k] .>= transactional_data[t,:]) for k in axes(X_input,2))`) is barely longer and generalizes — instructive in itself.
- **Assert-message mismatch for the allocation constraint** (line ~279): the assert counts `MOI.EqualTo` constraints, but a student who faithfully copies the lecture's `>= 1` constraint gets `GreaterThan` constraints and a message claiming they have the wrong *number* of constraints — the actual problem is the sense. Extend the message: "…Did you use `==` rather than `>=`? Each SKU must be allocated exactly once here."
- **Notation nits:** table header `$t_{mi}$` (line ~24) vs. the lecture's `$t_{m,i}$`; prose uses code-style "(i,j)" and "Q[i,j]" (line ~22) where $q_{ij}$ would match the lecture; "QMKP" (line ~77) is never expanded in the tutorial — define it on first use (Quadratic Multiple Knapsack Problem).

## 3. Content & robustness

- **Stray `#| eval: true` on a scaffold cell** (line ~286): the capacity-constraint "YOUR CODE BELOW" cell is the only scaffold with `eval: true` (all others are `eval: false`). Harmless while empty, but partially-completed student code in that cell breaks the render; almost certainly a typo for `false`.
- **`Pkg.add` at render time** (lines ~180–186): three hidden `Pkg.add` calls run on every render; slow, network-dependent, and bypasses `Project.toml` (which currently lists none of JuMP/HiGHS/Ipopt/Juniper). Course-wide pattern, but worth consolidating into the project environment.
- **Comment says "First set of transactions (1-20)"** (line ~118) with no matching "(21-40)" marker — either add the second marker at row 21 or drop the first. (Data itself checks out: 40 rows, 12 columns, and the assert target `Q[1,1] == 11` matches the data — Running Shoes appears in exactly 11 transactions.)
- **Heading hierarchy is flat** (lines ~171–345): "Use the Juniper solver", "Compute the coappearance matrix", …, "Count the number of split orders" are `##` siblings of the numbered sections, so the TOC shows Section 4 followed by eight unnumbered same-level entries and then "5.". Demote the implementation steps to `###` under Section 4.

## 4. Pedagogy & polish

- **Term inconsistency "split orders" vs. "split parcels":** Section 3 is titled "Counting Split Parcels", the text asks for "the number of split orders", and the variable is `number_of_split_parcels` (lines ~66–72); the counting section (line ~345) repeats the mix. With two warehouses the counts coincide, but only because $|\mathcal{K}| = 2$ — pick one term (and a one-liner noting that with more warehouses one split *order* can mean several extra *parcels* would be a nice aside).
- **English variant mix:** "maximise" (~57), "optimisation" (~68, ~347), "minimisation" (~77) vs. "Maximizing" (~50), "optimize" (~16), "Analyzing" (~408). Pick one (the lecture titles use American English).
- **Garbled bonus question** (line ~77): "another solution that has less split or the same number of split parcels" → "another allocation with fewer (or the same number of) split parcels".
- **Awkward/incorrect phrasing:** "Based on the output of the optimisation, we don't know the number of split orders yet" (~68, similar ~347) → "The objective value alone does not tell us the number of split orders."; "Juniper is a solver for nonlinear problems, that can be used" (~173) → drop the comma; "Note, that this does not work" (~177) → "Note that"; "I recommend to stick with Juniper" (~177) → "recommend sticking with"; "manually by hand" (~22, ~57) is redundant — "by hand" suffices.
- **Style nits in the provided print code** (lines ~329–340): the allocation loop iterates `for k in warehouses` (names) while the capacity loop uses `for k in 1:length(warehouses)` (indices) with `warehouses[k]` lookups, and `value.(X[i,warehouses[k]])` broadcasts over a scalar — use `value(...)` and `eachindex(warehouses)` for a cleaner model for students to imitate.
