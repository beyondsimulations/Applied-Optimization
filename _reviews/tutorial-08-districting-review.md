# Review: tutorial-08-districting.qmd

**Reviewed:** 2026-07-07
**Scope:** Pedagogy, model formulation, math notation, code, content robustness, writing polish

## Summary

A strong debugging-style tutorial: the "fix 6 mistakes" format is engaging, the mistakes are well chosen (I verified the buggy cell against `solutions/session-08/tutorial-08-districting.jl` — there are exactly the promised 6), and the difficulty ramp across Tasks 1–4 is well judged. The two main problems: a cell explicitly labeled "no mistakes" calls `Random.seed!(42)` without `using Random` anywhere, so students crash before reaching the intended exercise; and the random candidate-location draw makes the instance non-reproducible (broken seed) and, with roughly 3% probability, makes Task 3 infeasible through no fault of the student.

## 1. High-impact teaching improvements

- **`using Random` is missing — the "no mistakes" cell crashes** (lines ~64–78). The package cell (line ~66) loads JuMP, HiGHS, DelimitedFiles, Shapefile, DataFrames, Plots but not `Random`, yet the next cell — introduced with "Again, no mistakes!" — calls `Random.seed!(42)` (line ~78). Students get `UndefVarError: Random` inside a cell they were told is correct, which poisons the whole "find the 6 mistakes" premise. Add `using Random` to the package list. (The solution file has no seed at all, confirming the seed was bolted on later without updating the imports.)
- **Seed placement defeats its purpose.** The seed is set in the data-loading cell (line ~78), but `rand` is called in the mistakes cell (line ~115). Every re-run of the mistakes cell while debugging — which students will do many times — redraws `rangeDepartments` and changes the problem instance. Consequences: (a) the Task 2 gap comparison (line ~300) may compare objective values from *different instances*; (b) no reference objective value can be given for Task 1's "validate that your solution makes sense" (line ~44). Move `Random.seed!(42)` into the mistakes cell directly before the `rand` call (marked "This line is correct!"), then you can also state the expected optimal objective as a checkpoint.
- **Task 3 can be infeasible for an unlucky draw.** I computed from `data/drivingTimes0510.csv`: BA 503 has only 18 of 510 locations within 20 minutes. The chance that `unique(rand(1:510, 100))` contains none of them is (1 − 18/510)^100 ≈ 2.8%. Those students get a genuinely infeasible model, and `print_model_status` then reports "The model was not solved correctly. Have you corrected all mistakes?" — pointing them at their own (correct) code. Fixing the seed (previous two points) makes this deterministic; verify the seeded draw covers all BAs, or add a callout: "If the solver reports infeasibility, a BA may have no candidate department within 20 minutes — re-draw the locations."
- **State the target model mathematically in Task 1.** Students are asked to debug code against a model they must reconstruct from memory of the lecture — and the lecture's objective (lecture-08, line ~528) is written as $\sum \sum t_{i,j} \times X_{i,j}$ *without* the incident weights, while the code correctly uses `weightedDriving[i,j]` = $t_{i,j} \cdot w_j$. Print the full p-median formulation (with weights, $\min \sum_{i}\sum_{j} w_j t_{i,j} X_{i,j}$, all three constraints, binary domain) at the start of Section 1. This makes the debugging exercise a true math-to-code exercise and fixes the weight omission the lecture formula leaves open.
- **Surface the `2 * X[i,j] <= X[i,i]` teaching moment** (line ~138). This planted mistake is a near-copy of the lecture's compactness constraint $2X_{i,j} \leq \sum_{v \in \mathcal{N}_{i,j}} X_{i,v}$ (lecture line ~849) — students who attended may hesitate to "fix" it. After the task, add one question: "One of the six mistakes resembles a constraint from the lecture. Which one, and why is it wrong *here*?" (Answer: with a binary right-hand side of at most 1, `2X[i,j] ≤ X[i,i]` forces `X[i,j] = 0` for all $i \neq j$, which together with the assignment constraint makes the model infeasible.)

## 2. Model & notation issues

- **Symbol mismatch with the lecture** (line ~320): Task 3 calls the driving time $d_{i,j}$, but the lecture consistently uses $t_{i,j}$ (lecture lines ~448, ~528). Use $t_{i,j}$.
- **The conditional-constraint demo is semantically infeasible** (lines ~244–254): `conditionalConstraint` forces `X[i,j] == 1` for *every* department–BA pair closer than 1.5, which contradicts the single-assignment constraint the moment a BA is adjacent to two candidate locations. It is `eval: false` and uses the name `model`, but a student who pastes it into `pMedianModel` breaks their model in a confusing way. Use a harmless illustration (e.g., `X[i,j] <= 1`) or add "syntax illustration only — do not add this to your model".
- **The demo also reuses the name `model`** (lines ~246, ~260) — the exact identifier that was one of the six planted mistakes at line ~110 ("`set_attribute(model, ...)`"). Seeing `model` used again as if legitimate right after the debugging task undermines the lesson; name it `pMedianModel` or a clearly fake `some_model`.
- **"Within 20 minutes" is ambiguous about strictness** (lines ~318–320, ~350): the solution forbids assignments with `drivingTimes[i,j] >= 20` (Task 3) and requires backup with `drivingTimes[k,i] < 20` (Task 4), i.e., "strictly less than 20". State "strictly less than 20 minutes" (or "at most") in both task descriptions so students are not marked wrong on the boundary.
- **Adjacency threshold boundary** (line ~273): adjacency is defined as distance "less than 1.5"; the intended contiguity constraint applies to non-adjacent pairs, which the solution filters with `> 1.5`. On this hexagonal grid the second ring sits at ≈1.73, so no distance falls on 1.5 exactly and this is safe — but saying "at least 1.5 means not adjacent" would remove the students' doubt about which side gets the equality.

## 3. Content & robustness

- **`Pkg.add("Shapefile")` executes on every render** (lines ~56–60): the cell has `output: false` but not `eval: false`, so each `quarto render` runs a package-add against the shared `../applied-optimization` environment (activated by the include at line ~25). Consider `eval: false` for the render while keeping the cell for students, as done for the other instructional cells.
- **`print_model_status` ignores its argument** (lines ~152–166): the function takes `model` but hardcodes `pMedianModel` in all eight body references, plus a stray `begin ... end` block. It works only because `pMedianModel` is global — a bad pattern to model in a cell labeled "No mistakes here!", and it silently reports the wrong model if anyone ever passes a different one. Replace the body's `pMedianModel` with `model`.
- **`visualize_departments` reads the global `rangeDepartments`** (lines ~196, ~200) despite taking `hexshape, X, p` as parameters — same pattern; pass it as a fourth argument.
- **Cross-file note on the official solution** (`solutions/session-08/tutorial-08-districting.jl`): the gap cell hardcodes a reference objective `326607.39` — meaningless while the instance is random (see Section 1) — and prints `"The gap is $(gap)%."` where `gap` is a fraction, so a 5% gap prints as "0.05%". Worth fixing together with the seed.
- Data files, shapefile pair, and code-links in the front matter (lines ~4–20) all resolve to existing files in `tutorials/data/` — no issues found.

## 4. Pedagogy & polish

- **Duplicated phrase** (line ~73): "We then define the number of departments, load the data into scope and define the number of departments and the weighted driving times" — drop the first occurrence. Same line: "relative to the location notebook file" → "relative to the location of the notebook file".
- **Heading capitalization** (line ~38): "P-Median Problem" vs. the lecture's consistent "p-Median" (lowercase p is the standard convention); also "Modelling" (British) vs. the American spellings used elsewhere in the file ("modernization", "optimize").
- **Typos:** "Furthermore,we" missing space (~256); "If you computer cannot determine" → "If your computer" (~311); "should have shrinked" → "should have shrunk" (~338); "Unfortunate, the model was not solved correctly" → "Unfortunately" (~172); "answering the question in cell below" → "in the cell below" and "use the cell, to compute" has a spurious comma (~300); "backup support within 20 minutes of the driving time" → "within 20 minutes of driving time" (~350).
- **"euclidian" misspelling** in variable names and data file names (`euclidianDistances`, `euclidianDistances0510.csv`, throughout): correct is "Euclidean". It is at least used consistently, and renaming the data files would ripple through solutions and freezes — low priority, but worth fixing on the next data refresh.
- **Gap task could be more precise** (line ~300): say which gap is meant — the relative increase in objective value caused by the contiguity constraints, $(z_{\text{contig}} - z_{\text{base}})/z_{\text{base}}$ — and prompt the expected direction (the objective can only get worse when constraints are added), which is itself a small teaching moment.
